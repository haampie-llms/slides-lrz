Introduction

Sharing a software environment

  • A researcher / colleague wants to reproduce your results
  • You move from a laptop or VM to a cluster
  • You build a stack in CI for your users
  • The same stack on several clusters, or on short-lived cloud instances
  • A container for Kubernetes, JupyterHub, Apptainer…
Many ways in which you can share an "environment": a list of packages, exact versions, binaries, or a whole file system.
Introduction

Spack offers various ways to share software stacks

spack.yaml
abstract specs + config, like hdf5@1.14
when to use different machines
spack.lock
concrete dependency graph: all resolved packages, their versions, variants, architecture, platform.
when to use ~identical machines
build cache
binaries archived as *.tar.gz
when to usecompatible machines
container image
binaries + OS user land
when to usedeployment, sharing with non-Spack users

There are other ways I won't cover in this talk, namely central installations with

  • environment modules (module load hdf5)
  • Spack environment views (like Python virtual environments)
  • an upstream database for Spack users

Environments recap

spack.yaml and spack.lock

spack.yaml: input for the solver

spack:
  specs:
  - hdf5+mpi
  - mpich
  - py-h5py
  view: false
  concretizer:
    unify: true

Abstract specs + configuration. Meant to be human-readable.

spack.lock: input for the installer

{"roots": [{"hash": "jceyzq7…", "spec": "hdf5+mpi"}, …],
 "concrete_specs": {
  "jceyzq7…": {"name": "hdf5", "version": "1.14.6",
    "arch": {"platform_os": "ubuntu26.04",
             "target": "x86_64_v3"},
    "dependencies": [{"name": "cmake", "hash": "a4wqsr7…",
                      "parameters": {"deptypes": ["build"]}},
                     …]},
  "yc4n2pp…": {"name": "glibc", "version": "2.43",
    "external": {"path": "/usr"}, …},
  …59 nodes…}}

The fully concrete DAG: every version, variant, target and dependency, keyed by hash. Generated by spack concretize.

$ spack env create my-env
$ spack -e my-env add hdf5+mpi
$ spack -e my-env concretize   # creates spack.lock
$ spack -e my-env install

Sharing spack.yaml

spack.yaml is "portable"

On another machine, re-concretization uses that machine's:

  • Spack version and package repository commit
  • compilers and externals (packages.yaml)
  • OS, CPU target, available binaries (reuse)

So the result is "the same software, appropriate for this machine".

You can pin the things you care about:

spack:
  specs: [hdf5+mpi, mpich, py-h5py]
  repos:
    builtin:
      commit: 6427933d…  # or tag/branch
  packages:
    all:
      require:
      - target=x86_64_v3 # don't tune for my laptop
    hdf5:
      require: "@1.14"
Good for "same software". Not good for "exactly what I ran last month".

Sharing spack.lock

spack.lock is machine-specific

Machine specific target=znver3 or target=cannonlake

Externals are part of the DAG and of every dependent's hash. They record a prefix on this machine.

This makes sharing difficult across different machines.

Typical externals on HPC systems:

libcglibc: always
compilersystem / vendor gcc, oneAPI, nvhpc
MPIvendor MPI tuned for the fabric
GPUCUDA, ROCm, Level Zero drivers
schedulerSlurm, PMIx, libfabric/UCX providers
packages:
  mpi:
    buildable: false
  intel-oneapi-mpi:
    externals:
    - spec: intel-oneapi-mpi@2021.14
      prefix: /opt/intel/oneapi
  slurm:
    externals:
    - spec: slurm@24.05
      prefix: /usr
libc

glibc is more or less a required external

  • Since Spack v1.0, libc is an explicit node in the DAG: [e] glibc@2.43
  • Binaries link against symbol versions such as GLIBC_2.38. They run on a glibc that is at least as new.
  • The concretizer only reuses a binary if it is libc-compatible with the host
Build on the oldest glibc you need to support.

A laptop on Ubuntu 26.04 builds binaries that will not run on a SLES 15 cluster. Containers move this assumption into the base image (part 3).

Sharing binaries

Build caches

$ spack mirror add --unsigned mycache file:///shared/cache
$ spack -e myenv buildcache push --update-index mycache
# elsewhere: same mirror config + spack.lock
$ spack -e myenv install  # fetch binaries, no builds
  • One tarball per package (+ spec metadata), on a file system, S3, HTTP, or an OCI registry
  • --update-index rebuilds the index used for reuse by the concretizer
  • Signed by default (spack gpg); --unsigned for trusted locations

Relocation

Binaries embed absolute paths (RPATHs, scripts, config files). On install, Spack rewrites them to the new prefix. Strings in binaries can only shrink, so build with a padded install root:

config:
  install_tree:
    root: /opt/spack
    padded_length: 128
Sharing binaries

Two ways to use a build cache

Build cache + spack.yaml (reuse concretization)

# both machines configure the same mirror
$ spack env create myenv spack.yaml
$ spack -e myenv concretize  # reuses binaries
$ spack -e myenv install     # builds the rest
  • Each machine concretizes for itself; the cache is a source of reusable binaries
  • Reusable specs are installed from the build cache, others built from source
  • Works well when B has a glibc version ≥ that of A
As much reuse as possible.

Build cache + spack.lock

# reproduce A's DAG on B without source builds
$ spack env create myenv spack.lock
$ spack -e myenv install --cache-only
  • Machine B installs the exact* same binaries built on A
  • Works when machine B is equivalent to A: CPU target, externals
  • * "Exact" up to relocation: a different install root means rewritten paths in binaries and scripts
The same binaries, installed by Spack, on a compatible host.
Two different mindsets. Left: the cache is an accelerator; you trust the concretizer to pick what fits and fall back to source builds. Right: the cache is an archive of what was built on A; anything that would need a build is an error. Even then it's not bit-for-bit: binaries are relocated to B's install root, and externals resolve to B's /usr.

Sharing tips

Keeping environments shareable

Config includes can help

spack:
  specs: [hdf5+mpi, mpich, py-h5py]
  include:
  - path: ./site/cluster-a.yaml
    when: hostname.startswith("login")
  - path: ./site/laptop.yaml
    when: platform == "darwin"

Site specifics (externals, compilers, install root) go in included site scopes, not in spack.yaml.

Using few externals

  • Just let Spack build things, including cmake, python, zlib, …
  • Use externals when necessary: closed-source libfabric, Slurm/PMIx, ...
  • I personally don't use spack external find

How other tools handle "externals"

EESSI (CVMFS) / Nix / Guix

Ship their own libc (or libcs) at a particular absolute path like

  • /cvmfs/foo.cern.ch/...
  • /nix/store/...
  • /gnu/store/...

Conda / pip

Link against old glibc and assume compatibility, largely similar to Spack.

Spack v1.4?

I'm looking at a way to make glibc installable like any other package, which would eliminate the remaining external; we'd support both approaches.

Container images
using spack containerize

What you know

Build with Dockerfile

FROM ubuntu:24.04
RUN apt-get update && \
    apt-get install -y gcc
COPY app.c /src/
RUN gcc -o /usr/bin/app /src/app.c
$ docker build -t myorg/app:1.0 .
$ docker push myorg/app:1.0
  • Each step runs inside a container of the previous state.
  • File system changes are captured as a new layer (available thanks to overlayfs).
Familiar ground for everyone. Keep the two points that matter later: layers are diffs stacked in order, and a change invalidates everything after it.
spack containerize

Generate a Dockerfile from an environment

spack:
  specs:
  - hdf5+mpi
  - mpich
  - py-h5py
  packages:
    all:
      require: [target=x86_64_v3]
  container:
    format: docker    # or singularity
    images:
      os: ubuntu:24.04
      spack: "1.2"
$ spack containerize > Dockerfile
$ docker build -t hpc-env .
  • images:
    • For build and runtime environment
    • Spack-provided images like spack/ubuntu-noble:1.2,
    • or custom build / final images, e.g. an NVIDIA CUDA base with CUDA as an external
  • os_packages: distro packages for the build or final stage
  • strip, labels
  • format: singularity writes a .def file
  • Jinja2 template extension for customization
spack containerize · generated (trimmed)

A multi-stage build

# Build stage with Spack pre-installed and ready to be used
FROM spack/ubuntu-noble:1.2 AS builder

RUN mkdir -p /opt/spack-environment && set -o noclobber \
&&  (echo spack: \
&&   echo '  specs:' \
&&   echo '  - hdf5+mpi' \
     …
&&   echo '  config:' \
&&   echo '    install_tree:' \
&&   echo '      root: /opt/software' \
&&   echo '  view: /opt/views/view') > /opt/spack-environment/spack.yaml

RUN cd /opt/spack-environment && spack env activate . && \
    spack install --fail-fast && spack gc -y

...

# Bare OS image to run the installed executables
FROM ubuntu:24.04
COPY --from=builder /opt/spack-environment /opt/spack-environment
COPY --from=builder /opt/software /opt/software
COPY --from=builder /opt/views /opt/views
...
ENTRYPOINT [ "/entrypoint.sh" ]
CMD [ "/bin/bash" ]
  • The builder image provides Spack, compilers and the same OS as the final stage
  • Note: it ships spack.yaml, not spack.lock. It concretizes inside the build.
  • One RUN step installs everything, so it becomes one big layer
  • The final stage copies /opt/software and adds an entrypoint that activates the environment
spack containerize

Trade-offs

Pros

  • Isolated build environment
  • Self-contained, reviewable recipe
  • Singularity/Apptainer definition files for HPC
  • Can apt/yum install ... extras if needed

Cons

  • Needs a builder (Docker, Podman, Buildah, Apptainer), not always available (or requires root)
  • Everything in one RUN: any change to spack.yaml rebuilds everything; a failure throws away all finished dependencies
  • Debugging a failed build inside a container build is painful
  • One fat layer: no sharing between different images/tags
spack containerize

Hybrid: give the Dockerfile a build cache

# generated Dockerfile, install step edited by hand
RUN --mount=type=bind,from=buildcache,target=/mnt/cache \
    cd /opt/spack-environment && \
    spack env activate . && \
    spack mirror add --unsigned host /mnt/cache && \
    spack install --fail-fast && spack gc -y
$ docker build \
    --build-context buildcache=/shared/cache \
    -t hpc-env .
  • A file system build cache on the host is visible only during that RUN, so it doesn't end up in a layer
  • spack install fetches what it can reuse, builds the rest
  • Only binaries compatible with the builder image are reused: a cache built on a newer host glibc doesn't help
  • Can't easily add to build cache during build (read-only).
  • Still one fat layer, still needs a builder
What if a build cache and a container image were the same thing?
Tested with Docker 29.8 + BuildKit: --build-context makes a host directory available as a named context, RUN --mount=type=bind,from=… exposes it during one step. With rw you can write, but the writes are thrown away. type=cache mounts persist between builds, but live in BuildKit's own storage, not on the shared file system.

What is behind a tag?

A manifest, a config, and tarballs

  • docker pull: resolve the tag, fetch the manifest and blobs, unpack the tarballs in order, start a process with the config's environment
  • docker push: upload the blobs, then the manifest, then point the tag at it.

The key observation

A Spack build cache tarball is already a layer

A layer is a tarball that gets unpacked at /. Spack's build cache tarball of a package contains its files at their install prefix:

$ curl -s localhost:5000/v2/hpc/blobs/sha256:829c… | tar -tz
home/bot/lrz-demo/store/linux-x86_64_v3/zlib-ng-2.3.3-g72d…/
home/bot/lrz-demo/store/…/zlib-ng-2.3.3-g72d…/include/zlib.h
home/bot/lrz-demo/store/…/zlib-ng-2.3.3-g72d…/lib/libz.so.1
…

Unpack it on top of a base image and the package is exactly where it was built. A build cache is one manifest away from being an image.

spack buildcache push

Archive what is installed

# --base-image: provides glibc + the rest of the OS
# --tag: one image for all roots + runtime deps
# mirror: or oci+http://localhost:5000/… for local tests
$ spack -e . buildcache push \
      --base-image ubuntu:26.04 \
      --tag hpc-env \
      oci://ghcr.io/myorg/buildcache
  • Input: installed specs (built on the host, so easy to debug)
  • Output:
    • Container image tagged
      ghcr.io/myorg/buildcache:hpc-env
    • and per-package tags
      ghcr.io/myorg/buildcache:name-version-hash.spack
  • No Docker / daemon / root access needed.
  • Credentials via env vars:
    spack mirror add --oci-username-variable U --oci-password-variable P name oci://…
  • Without --base-image you get a "distroless" image: a fine build cache, but not runnable

Consequences

Archiving instead of building

You get

  • Deduplication: images that share dependencies share layers, in the registry and in the runtime's local store
  • Incremental pushes: only new builds are uploaded
  • Building on the host is easier to troubleshoot
  • No root needed
  • The container registry serves both spack install and docker run

Things to be aware of

  • You need to pick a base image with compatible glibc
  • Use generic targets like target=x86_64_v2 for CPU compat
  • The install paths: /home/me/spack/opt/… ends up in the image. Use a neutral install_tree: root: /opt/spack.
  • One architecture per tag (no multi-arch index)
  • Some limitations to max number of layers
Limitation

How many layers can an image have?

Overlay-based runtimes mount every layer as an overlayfs lowerdir. Spack makes one layer per package, and large environments easily reach 150+ packages.

runtime / storagemax layers
Docker, classic overlay2 driver125
Docker ≥ 29 (fresh install): containerd image store499
Podman (containers/storage)≈ 500
Apptainer, Enroot, Charliecloudno limit: flatten
// moby: daemon/internal/layer/layer_store.go
// maxLayerDepth represents the maximum number of
// layers which can be chained together. 125 was
// chosen to account for the 127 max in some
// graphdrivers plus the 2 additional layers
// used to create a rwlayer.
const maxLayerDepth = 125

The kernel's own overlayfs limit is about 500 lower layers, which is what containerd and Podman run into.

Measured with rootless Docker 29.8 on Linux 7.0, see the next slide.

Spack docs currently say 128; the precise number for overlay2 is 125 including the base image layers. Docker 29 made the containerd image store the default for new installs; upgraded installs keep overlay2.

Layer limit

Working around layer limits

  • Smaller images: push subset of environment
    spack buildcache push --tag x mirror hdf5 python
  • Flattening runtimes (Apptainer, Enroot, Charliecloud) don't have the limit at all
  • Request me to implement a form of layer squashing
  • Use some externals from base image; that's again the externals ↔ base image trade-off.
Aside

Containers don't solve all the runtime problems

The container's MPI must talk to the host's launcher (Slurm/PMIx) and fabric (libfabric/UCX providers, drivers).

  • Hybrid: an MPI inside the image that is compatible with the host's process manager and fabric, launched with srun / mpiexec from outside
  • Bind: mount the host's MPI over the container's. Requires ABI compatibility: the MPICH family (MPICH, Intel MPI, Cray MPICH) shares an ABI; MPI 5.0 standardizes one.
  • GPU drivers / libcuda.so are outside of Spack's scope, they are from the system.

Spack v1.2 · June 2026

Concretization groups

Bootstrap a compiler: needs:

spack:
  specs:
  - group: compiler
    specs: [gcc@15.2]

  - group: apps
    needs: [compiler]
    specs:
    - hdf5 %gcc@15.2
    - libtree %gcc@15.2

The groups listed in needs: are concretized first, and their specs can be reused.

CPU and CUDA builds: override:

spack:
  specs:
  - group: cpu
    specs: [gromacs, lammps]

  - group: cuda
    specs: [gromacs, lammps]
    override:
      packages:
        all:
          prefer: ["+cuda cuda_arch=90"]
  view: false

The override is a config scope for that group only.

The same override pattern works for targets (x86_64_v3 vs v4) or CUDA vs ROCm. view: false because both groups have a gromacs root, which would clash in a single view.

Isolation of Spack itself

Spack is currently "installed" with git clone, and modifies files inside its dir, like $spack/opt/spack, $spack/var/spack/environments, GPG keys, licenses…

Shared Spack: user data goes into XDG locations:

~/.config/spack       # config (was ~/.spack)
~/.local/share/spack  # installs, envs, keys
~/.local/state/spack  # misc cache, repos
~/.cache/spack        # caches

What this enables

  • pip install spack, distro packages
  • Single Spack instance can be installed globally and used by multiple users

Existing clones

After a git pull, Spack asks before it copies environments, keys and licenses.

Spack v1.3 · in progress, not merged yet

Usages: variants on dependency edges

Some options change how a dependency is used, but not the dependency itself:

  • when using gcc, enable ASan
  • when using gcc, write SARIF diagnostics

As a variant on gcc, this changes gcc's hash: gcc gets rebuilt, and every package in the DAG has to agree on the value.

A usage sits on the edge: it changes the hash of the dependent, and gcc stays the same.

Spec syntax (subject to change)

zlib-ng %[usages=+sarif] gcc
foo %[usages=+sarif sanitizers=asan] gcc
foo ^[deptypes=link usages=+sarif] mpich

Declared by the dependency

class Gcc(Package):
    usage("sarif", default=False,
          description="emit SARIF diagnostics")

Similar to variant()

Spack v1.3 · planned for November 2026

Deprecations with a reason and a severity

Package authors

class Openssl(Package):
    version("3.0.7", sha256="…")
    version("1.1.1t", sha256="…")

    deprecated("@1.1.1t", reason="vuln",
               severity="high",
               labels=["CVE-2023-0286"])
  • reason: vuln, rename, retired or unspecified
  • severity: low … critical, following CVSS ratings
  • Replaces version(…, deprecated=True): now any spec, e.g. deprecated("@1.2 +foo", …)

Sites and users

packages:
  all:
    deprecation:
      allow:
      - reason: [rename, retired, unspecified]
        severity: low
      - reason: vuln
        severity: none
  • Not every CVE is as critical; it depends on the context.
  • Nothing is allowed by default: a deprecation that isn't allowed is an error
spack/spack#52372, on develop. Package API v2.6. By default nothing is allowed, so Spack does not select a deprecated version unless the configuration says so. Selectors can also match labels (CVE/GHSA ids), so a site can allow specific advisories it has assessed.
